# Требования к тирам KV-кэша (VRAM + RAM + FS), метрики и методика приёмки

Статус: черновик-спецификация, по нему ведётся дальнейшая работа.
Область: `vllm/v1/kv_offload/**`, `vllm/distributed/kv_transfer/kv_connector/v1/offloading/scheduler.py`.
Профиль: GLM/Qwen-класс 27B, GGUF IQ3_S + MTP, TP=2, 2×V100-16GB (SM70), flash-attn V100.
Документ заменяет ранее использовавшийся `fs-tier-task-contract.md` в части критериев AC-1/AC-2:
формулировки там арифметически недостижимы (см. §7), ниже — выполнимые.

---

## 1. Определение смысла тиров

### 1.1 Термины

**Блок** — единица KV-кэша: `block_size` токенов (1024 для attention-групп 0–7, 512 для группы 8).
У блока есть ключ `OffloadKey` и **хэш цепочки**: ключ блока `k` зависит от содержимого всех токенов
`[0, (k+1)·block_size)`. Следствие: префикс адресуем только как непрерывная цепочка от блока 0.

**Тир** — уровень хранения блоков:
* **T0 = VRAM** — пул KV на GPU (`--kv-cache-memory-bytes`), источник истины для forward;
* **T1 = RAM** — первичный offload-тир (`--kv-offloading-size`), принимает блоки, вытесняемые из T0;
* **T2 = FS** — вторичный тир (`TieringOffloadingSpec`, `root_dir`, `max_bytes`, `state_max_bytes`).

**Резидентность** — блок существует хотя бы в одном тире в момент запроса.
**Ожидаемый набор E** — блоки префикса запроса, которые мы уже префилили раньше (то есть блок был
произведён и хотя бы раз предложен к сохранению).
**Резидентный набор P ⊆ E** — из них резидентные в момент запроса.
**Возвращённый набор A ⊆ P** — фактически отданные движку (external hit, за которым последовал перенос).

### 1.2 Требования

**R-1 (полнота возврата).** `A = P`. Всё, что лежит в T0 ∪ T1 ∪ T2 в момент повторного запроса,
должно быть возвращено. Метрика: `A/P = 1.00`.

**R-2 (непрерывность цепочки).** Возврат обрывается только на блоке, которого нет ни в одном тире.
Ни один резидентный блок не может быть пропущен из-за дырки в середине цепочки.
Метрика: `gap_orphans = |P \ A| = 0`, плюс фиксируется `gap_at` — индекс блока, оборвавшего цепочку.

**R-3 (целостность записи).** Каждый блок, принятый к сохранению, либо подтверждён записанным, либо
явно учтён как refused (не принят). Молчаливых потерь нет: `lost = 0`, `store_failed = 0`,
`load_errors = 0`, `drift = 0`, `out/new = 1.00 ± 1 блок`.

**R-4 (достоверность чтения).** «Попадание» без фактического переноса данных попаданием не считается:
`fs_loaded_blocks / fs_hit_blocks ≥ 0.98` (по интервалу, см. §6).

**R-5 (сохранность через перезапуск).** Префикс, однажды запрефиленный и сохранённый, доступен после
рестарта процесса без повторного префилла. Метрика: `U1 > 0` на первом запросе после рестарта при
пустом T1 (§5.5).

### 1.3 Что НЕ требуется

* Возврат хвоста промпта: последние блоки запроса — это новый текст, они не префилились и в E не входят.
* Возврат вытесненных блоков: если блок вытеснен из всех тиров, R-1 на него не распространяется;
  он переходит в отчёт о ёмкости (§4, группа E).
* «Ноль вытеснений» как самоцель. При рабочем наборе у капа вытеснения неизбежны; требование —
  чтобы вытеснение не рвало живые префиксы (см. §8.2).

## 2. Архитектурное следствие из R-1/R-2

Так как цепочка непрерывна, а вытеснение сейчас **поблочное** (`DirCapacity` выбирает жертвы поштучно
по времени последнего обращения), префикс получает дырки, и всё, что после дырки, становится
недостижимым при том, что физически лежит на диске. Это наблюдалось: 41 648 блоков в прогоне 7 были
резидентны в RAM и не возвращены (4.4 % резидентного), 1 221 запрос получил ноль блоков при их наличии.

Отсюда требование к политике вытеснения:

**R-6 (вытеснение целыми префиксами).** Жертвой вытеснения может быть только целая цепочка (префикс),
либо запрещается вытеснять блок `k`, пока резидентен блок `j > k` той же цепочки. Реализация —
отдельная задача (см. §8.2); без неё `A/P = 1.00` недостижимо при рабочем наборе у капа.

## 3. Слоистое разложение промпт-токенов

Движок уже отдаёт разделение по источнику (используется вместо суррогатного `R`):

```
vllm:prompt_tokens_by_source_total{source="local_compute"}        # честный префилл
vllm:prompt_tokens_by_source_total{source="local_cache_hit"}      # попадание в T0 (GPU prefix cache)
vllm:prompt_tokens_by_source_total{source="external_kv_transfer"} # попадание в T1/T2
vllm:prompt_tokens_total
```

Согласованность: сумма трёх источников должна совпадать с `prompt_tokens_total` с допуском 5 %.
На замере 2026-11-08 расхождение 4.4 % (1 491 847 против 1 560 852) — определение счётчика требует
сверки по коду до ужесточения допуска. `prompt_tokens_cached_total` считается иначе (включает и T0, и
внешние попадания с округлением до блока), поэтому как основной показатель не используется.

## 4. Набор метрик

Все отношения считаются **на интервальных дельтах** окна измерения, обе стороны — из одного скрапа
или одной строки лога. Кумулятивные значения сравнивать между собой нельзя.

### Группа A — целостность записи (R-3)

| ID | Формула | Источник | Порог |
|----|---------|----------|-------|
| S1 | `out / new` | `GROUPED-STORE` (блоки; `new` — только уникальные предложения) | `1.00 ± 1 блок` |
| S2 | `lost / new` | `GROUPED-STORE` | `0` |
| S3 | `store_failed`, `load_errors`, `drift` | `FS-METRICS` | `0` |
| S4 | `out / adm` | `GROUPED-STORE` | `1.00` (контроль) |

`refused / new` — не провал, а сигнал о ёмкости: печатается всегда, интерпретируется вместе с `E2`.

### Группа B — достоверность чтения (R-4)

| ID | Формула | Источник | Порог |
|----|---------|----------|-------|
| F1 | `fs_loaded_blocks / fs_hit_blocks` | `FS-METRICS` + `OFFLOAD-HIT-SPLIT`, один интервал | `≥ 0.98` |
| F2 | `promo_refused_blocks / sec_hit` | `TIER-STATS` | `≤ 0.05` |

F2 > 0.05 означает давление на T1 (попадание есть, поднять в RAM некуда) — это диагноз по ёмкости RAM,
а не отказ T2.

### Группа C — полнота возврата (R-1, R-2)

| ID | Формула | Источник | Порог |
|----|---------|----------|-------|
| C1 = A/P | `returned / (present_ram ∪ present_fs)` | `RETURN-AUDIT` (§8.1) | `1.00` |
| C2 = P/E | `present / expected` | `RETURN-AUDIT` | отчётная (ёмкость) |
| C3 | `gap_orphans = \|P \ A\|` | `RETURN-AUDIT` | `0` |
| C4 | `gap_at` | `RETURN-AUDIT` | диагностика |

До появления `RETURN-AUDIT` доступна верхняя оценка из `OFFLOAD-LOOK-DBG`: `present − hit` при
числовом `hit` (с оговоркой: часть таких строк — отложенные асинхронные пробы, `hit=None`, они
исключаются). Эта оценка **не** заменяет C1–C3, так как `present` покрывает только T1.

### Группа D — польза (зачем тиры нужны)

| ID | Формула | Источник | Порог |
|----|---------|----------|-------|
| U1 | `external_kv_transfer / prompt_tokens_total` | Prometheus | отчётная; сравнивается A/B (§5.6) |
| U2 | `fs_tokens / (ram_tokens + fs_tokens)` | `OFFLOAD-HIT-SPLIT` | отчётная |
| U3 | `local_cache_hit / prompt_tokens_total` | Prometheus | отчётная |
| U4 | TTFT p50/p95 | `vllm:time_to_first_token_seconds` | сравнение A/B |
| U5 | префилл-токены на запрос | `prompt_tokens_total / requests` | сравнение A/B |

`R = prompt_tokens_cached_total / prompt_tokens_total` остаётся как сводный индикатор, но
**не сравнивается** с блочным `r_req` из `OFFLOAD-LOOK-DBG`: разные слои (T0 + внешние против T1/T2),
плюс округление до блока даёт ±1 блок на запрос. Расхождение — диагностика, не критерий.

### Группа E — ёмкость и вытеснение

| ID | Формула | Источник | Порог |
|----|---------|----------|-------|
| E1 | `evicted_then_missed / evictions` | `FS-MISS-CLASS` (поле `evicted`) | `0` |
| E2 | `evictions / stored_blocks` | `FS-METRICS` (churn) | отчётная; `> 1` → рабочий набор не влезает |
| E3 | `state_bytes / state_max_bytes`, `state_evict_unread` | `FS-METRICS` | отчётная |

E1 — это и есть «блок ушёл из тира, а потом его спросили и не нашли». Именно он заменяет требование
«evictions = 0».

## 5. Методика тестирования

### 5.1 Замороженные параметры

Меняются только по явному решению; иначе прогон несравним:

```
--max-model-len 168340   --max-num-batched-tokens 2048   --max-num-seqs 4
--kv-cache-memory-bytes 5100273664   --kv-cache-dtype fp8_e4m3   --block-size 1024
--watermark 0.2   --scheduler-reserve-full-isl   TP=2
dflash spec 7 tokens   --attention-backend FLASH_ATTN_V100
T2: max_bytes 68719476736  state_max_bytes 8589934592  eviction_policy lru
```

`--kv-offloading-size` фиксируется отдельно для каждого кандидата (текущий тестовый профиль —
40 GB; продакшн-профиль — 16 GB) и указывается в отчёте.

### 5.2 Профиль нагрузки

10 параллельных one-shot сессий агента (по одной задаче на сессию), штатный профиль, без
специально созданных профилей. Длительность — не менее 15 минут непрерывной работы, при этом
сессии не дожидаются завершения. Первый прогон в серии — на **холодном** каталоге T2
(`root_dir` очищен), чтобы начальные попадания были честным нулём.

### 5.3 Сбор

* скрап `/metrics` не реже 1/10 с в начале (0–2 мин), затем 1/30 с, далее 1/60 с;
* журнал юнита с фильтром по `FS-METRICS|FS-MISS-CLASS|GROUPED-STORE|TIER-STATS|OFFLOAD-HIT-SPLIT|OFFLOAD-DEFER|OFFLOAD-LOOK-DBG|RETURN-AUDIT`;
* фиксируются старт юнита, `NRestarts`, наличие `OutOfMemory`/`Traceback` в журнале;
* `/health` и `/v1/models` опрашиваются до первого 200 — старт считается успешным только по ним.

### 5.4 Окно измерения

Окно начинается после прогрева (первые 2 минуты отбрасываются) и заканчивается по остановке
нагрузки. Все метрики §4 считаются дельтами за окно; отчёт содержит как дельты, так и последний
абсолютный срез.

### 5.5 Тест сохранности через перезапуск (R-5)

После основного прогона: остановить юнит, дождаться выхода, запустить снова на том же `root_dir`
(T1 пуст, T2 тёплый), послать по одному **идентичному** запросу в каждой из 10 сессий.
Ожидание: `U1 > 0` уже в первом запросе, `A/P` по доступным блокам — 1.00 для целых цепочек.
Этот тест отделяет «тир переживает рестарт» от «тир работает только на горячем RAM».

### 5.6 A/B по пользе

Тот же профиль нагрузки с **отключённым** вторичным тиром. Сравниваются U1, U3, U4, U5.
Разница между A и B — единственная честная мера вклада FS; внутренние счётчики её не заменяют.

### 5.7 Запрещено в рамках прогона

* менять параметры §5.1;
* перезапускать юнит во время окна измерения;
* смешивать кумулятивные и интервальные значения;
* докладывать отношения без абсолютных счётчиков, из которых они получены.

## 6. Округления и допуски

* Блок attention — 1024 токена, группа 8 — 512. Любая сверка «блоки ↔ токены» несёт ±1 блок на запрос.
* Допуск 2 % на F1 осмыслен только на окнах от десятков блоков.
* `GROUPED-STORE` и `OFFLOAD-HIT-SPLIT` — интервальные (счётчики сбрасываются после печати),
  `FS-METRICS` — кумулятивные с момента старта процесса. Смешивать нельзя, только дельта к дельте.
* `loaded_blocks` считает операции чтения, а не уникальные блоки: один блок, прочитанный дважды,
  даёт две операции. Поэтому F1 — отношение операций, а не «хит = блок».

## 8. Требуемая инструментация и работа

### 8.1 `RETURN-AUDIT` (обязательно для C1–C3)

Одна строка на запрос (не на шаг), под отдельным флагом:

```
RETURN-AUDIT req=<id> g=<group> expected=<N> present_ram=<a> present_fs=<b>
             returned=<c> gap_at=<i> orphan_after_gap=<d>
```

Реализация: пройти цепочку **не останавливаясь на первом промахе**, проверить наличие каждого ключа
в T1 (`contains`) и в T2 (`stat` пути), отметить индекс первого отсутствующего блока и число
резидентных блоков после него. Стоимость — один `stat` на блок, только в режиме аудита.

### 8.2 Вытеснение целыми префиксами (R-6)

Жертва — целая цепочка; либо запрет вытеснения блока `k` при резидентном `j > k` той же цепочки.
Без этого R-1/R-2 недостижимы при рабочем наборе у капа.

### 8.3 Счётчики

* развести пробы lookup на «исторические» (`idx < num_computed / block`) и «фронтирные»
  (`idx == num_computed / block`); фронтирные — только информационно;
* печатать `loaded_blocks` и `hit_blocks` одного интервала в одной строке `FS-METRICS`;
* вынести `evicted_then_missed` из `FS-MISS-CLASS` в `FS-METRICS`.

## 10. Изменения в этом PR

Три коммита поверх `main` (`ac249f1`), не меняющие ни одного параметра §5.1.

**`90f5762` — классификатор промахов FS** (`vllm/v1/kv_offload/tiering/fs/manager.py`):
`_classify_miss`/`_remember_stored`, строка `FS-MISS-CLASS misses=… never=… evicted=… hits=…`.
Отделяет «блок никогда не писали» от «блок был и вытеснен». Под `VLLM_FS_TIER_STATS=1`.

**`e729073` — необязательные профили прогрева** (`vllm/v1/worker/gpu/warmup.py`):
`_warmup_cycle_optional` перехватывает OOM на профилях, кроме первого; выключатель
`VLLM_SM70_MRV2_WARMUP_FULL=0`. Причина: расширенный прогрев MRV2 требует 486 MiB при 369 MiB
свободных на 16 GB V100, движок не открывает порт. Требует `os.environ` напрямую: переменные,
объявленные в `vllm/envs.py`, не доходят до `EngineCore`/`Worker_TP` в этом форке.

**`7e8480c` — write-through промпт-блоков** (`cpu/manager.py: resident_keys`,
`tiering/manager.py: persist`, `base.py: persist` по умолчанию no-op, `scheduler.py: _persist_prompt_blocks`
под `VLLM_SM70_PERSIST_PROMPT`): по завершении запроса его промпт-блоки пишутся вниз, в том числе в T2.
Причина: T1 отдавал в T2 только вытесняемое, а голова промпта не вытесняется — на диск она не попадала
никогда. Эффект: `loaded_blocks` 30 → 750, попадания FS 0.9 % → 4.8 % по пробам, доля T2 в возвращённых
блоках — около половины.
